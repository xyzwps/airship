# 规格册索引

规格册是 **airship 用户可见契约的唯一清单**。给人读、给人 review；可执行测试是它的影子，不是反过来。
这儿只放"看得见什么"，不放为什么、也不放实现：架构与依据看 [../architecture.md](../architecture.md)。

## 册子与用例放在它们管的代码旁边

```
src/shell/specs/*.md          壳的册子（窗口、主题、契约桥、授权、存储、子进程与工具、托盘、日志）
src/shell/tests/*.test.*      壳的用例；helpers/ 里是壳的测试替身与界面挂载器
src/apps/specs/*.md           应用注册、清单与 airship 包的规矩
src/apps/<id>/specs/*.md      每个应用一本（或多本）
src/apps/<id>/tests/*.test.*  每个应用的用例
src/sdk/tests/*.test.*        SDK 宿主的用例（SH-011 / SH-012 / SH-013 / SH-019 钉的是壳给的样子，
                              实现搬到了 SDK，用例跟着实现走；编号不动）
src/shared/<包>/specs/*.md    共享包一本；tests/ 放它的用例
docs/specs/index.md           这本索引——唯一跨区的文件，与架构文档同级
src/<区>/<名>/tests/fixtures/   真样本跟着用它的用例走（wslc 的真实输出在 src/apps/wsld/tests/fixtures/）
```

`just casecov` 递归找所有 `specs/*.md` 与 `tests/**` 里的用例，新加区域不用改检查器。
唯一的例外是 `templates/app/`：那是给外部作者复制的范本，里面的册子与用例还没落到某个真实应用上，
按目录名排除在差集之外（`just test` 也不跑它）；复制进 `src/apps/<id>/` 之后才归这套规矩管。

## 结构（固定四档）

```markdown
# bridge

## Purpose
一句话：这本册子管的是哪一块东西。

### Requirement: 这一条锁的是哪个不变量
依据：为什么这么定（一段，指向 architecture.md 的节）。

#### Scenario: BR-001 未声明的能力，界面上读得到为什么被拒
- **WHEN** vcp 未声明 settings，界面点"记住这套配置"
- **THEN** 错误条原样读得到「vcp 没有声明 settings 能力（要用它就在 apps/vcp/app.ts 的 capabilities 里声明）」
- **AND** 不出现 "Error invoking remote method" 这类 Electron 内部措辞
```

## 编号规则

- 每条 `#### Scenario:` 带稳定 ID，形如 `BR-001`，按能力前缀分组（见下面索引表）。
- **ID 是稳定句柄，不是阅读顺序**：册子按语义分节，新场景先选节、再取该前缀下的下一个号，
  所以全局 ID 不保证递增；要守的是**同一 Requirement 内按 ID 升序**。
- **ID 一旦提交不复用、不重排。** 删掉一条是显式评审动作，要说清为什么这条契约不再成立。三位号段，上限 999。
- **一条 Scenario ≤ 5 行**：判的是"这一条读不读得动"。

## 写法规矩

1. **只写可观察结果**。这里的"可观察"有四类，每一类都能被测试摸到：
   - 界面：看得见的文字、按钮标签、禁用态、点了之后变成什么；
   - 错误文案：抛给用户的中文句子原文；
   - 壳这一侧看得见的事：数据目录里真实生成的文件、日志行的形状、发给外部 CLI 的命令行与参数；
   - 几何与内存：实测数字（写在 architecture.md §3.1，册子里只写判据）。
   - ✗ `THEN settings 缓存命中`（键写错也能绿） → ✓ `THEN 重启后读到的还是刚才那本的书号`
2. **不写实现**：不出现类名、方法名、控件名。实现变了册子不该变。
   唯一例外是**系统边界上的契约**：与 `ffmpeg` / `wslc` 的调用契约（命令行、参数、退出码）和与壳的
   跨进程调用（能力位名、错误文案原文）。它们是外部真看得见的一面，允许出现，但仍不写由哪个类去发。
3. **一条 Scenario 只锁一个不变量。**
4. **bug fix 必须先补 Scenario**（描述现象），再补可执行用例，再改代码。
5. 界面观感（宽度、圆角、对齐）不进册子——那是 `just shot` 截图走查的事，产物不入代码库。
6. **写不出可执行判据的期望别进册子**。只能在真机上观察的东西（单实例锁、崩溃隔离、任务栏缩略图）
   记在 [../architecture.md](../architecture.md) 对应小节；册子里每一条都要有一个挂得上编号的用例。
7. 每条契约讲不清"为什么这样定"时，在 Requirement 正文里给一句指向 architecture.md 的引用，别把依据抄成长段。

## 与测试的绑定

可执行侧把 ID 写在用例标题开头：

```ts
it('SH-001 启动只出现启动器窗口', () => { … })
```

```bash
just casecov   # = vitest run spec-coverage，册里编号与用例编号做双向差集
```

册里有号、用例没挂 = 未实现；用例挂了号、册子里没有 = 私测（禁止）。
同一条契约需要多条用例钉住时，ID 重复出现即可；差集只看"有没有"，不看次数。

## 加一个新能力

索引表添一行、取一个没用过的两字母前缀、开一本新册子。
册子写完后跑 `just casecov`：漏挂的编号会逐条列出来。
