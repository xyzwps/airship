# theme

## Purpose
三档主题的选定与落地：每个应用自己操心自己的主题，每个窗口把主题落到自己那份文档上，"跟随系统"由谁算。
窗口与直跑的其余规矩见 `runtime.md`。

### Requirement: 每个应用改自己的主题档
主题属于窗口观感（与最小化/关闭同族），不走 settings 面；落在应用自己那份设置文件里，
runtime 不持有全局主题，也没有广播——一个应用改档，别的应用不跟着变。

#### Scenario: TH-002 应用改得了自己的主题，不碰设置面
- **WHEN** 一个一行设置都不碰的应用（生命游戏就是）改自己的主题档
- **THEN** 改得成，它自己那份设置文件里记下新档
- **AND** 每个应用窗口都拿得到 setter，不存在"只读"的答复

#### Scenario: TH-004 亮暗两档是直接落定的实际结果
- **WHEN** 点那颗键切到「亮色」
- **THEN** 发给 runtime 的请求里 mode 与 resolved 都是 `light`

#### Scenario: TH-012 标题栏上那颗主题键是图标，三档循环
- **WHEN** 看应用窗口标题栏上的主题键，从"跟随系统"起连点四次
- **THEN** 它是一颗图标键，画的就是当前档：跟随系统是半明半暗的圆、暗色是月牙、亮色是太阳
- **AND** 依次经过 暗色、亮色、回到跟随系统、再到暗色——循环不倒退也不跳档，界面上没有主题下拉框

#### Scenario: TH-013 那颗纯图标键念得出"现在哪档、点一下换成哪档"
- **WHEN** 把鼠标停在键上，或用读屏软件看它的无障碍名称
- **THEN** 悬停读得到「主题：暗色（点一下换成亮色）」，无障碍名称读得到「主题：暗色，点一下换成亮色」
- **AND** 档位名与实际循环一致，界面里不存在只有图标、悬停什么都不写的键

#### Scenario: TH-014 改档只动这个应用，别的应用不跟着变
- **WHEN** 两个应用各挂各的窗口，其中一个把主题从暗改成亮
- **THEN** 另一个读到的主题快照原样不动，它那份设置文件一个字节没变
- **AND** 不存在主题广播通道，改档的请求只写自己那份设置

#### Scenario: TH-015 "跟随系统"的实际亮暗由本窗口算好交给 runtime
- **WHEN** 系统偏好是暗色，点那颗键切到「跟随系统」
- **THEN** 发给 runtime 的请求带着 `system` 与实际算出的 `dark`
- **AND** 主进程自己不去猜系统偏好（它没有 matchMedia）

### Requirement: 每个窗口都得自己把主题落到文档上
窗口化之后每个窗口是独立文档：没人落地，整窗 CSS 变量就是空的。

#### Scenario: TH-005 窗口挂载后文档上带着实际生效的亮暗
- **WHEN** runtime 说现在生效的是暗色，应用窗口挂载起来
- **THEN** 这个窗口的 `<html>` 上 `data-theme` 是 `dark`，`color-scheme` 也是 `dark`
- **AND** 生效值换成亮色后，同一份文档跟着变成 `light`

#### Scenario: TH-006 桥还没回话时先按系统偏好画，避免白闪
- **WHEN** 主题查询还没返回
- **THEN** 首帧的亮暗取自系统的 `prefers-color-scheme`，不是空白或默认亮色

### Requirement: 主进程读主题时不编造实际值
`system` 档在渲染侧才算得准，主进程只兜底。

#### Scenario: TH-008 没记过主题时读出来是跟随系统
- **WHEN** 某应用的设置里还没写过主题
- **THEN** 读到的 mode 是 `system`
- **AND** resolved 回落成"上一次实际生效的那档"，默认 `light`

#### Scenario: TH-009 写过的档位原样读回
- **WHEN** 某应用的设置里记着 `{ mode: 'dark' }`
- **THEN** 读到的 mode 是 `dark`，resolved 也是 `dark`
