# package

## Purpose
一个 airship 包在磁盘上长什么样：它是一个 **zip 归档**，文件名 `<id>.airship`，里面的条目名就是包内路径。
这本册子钉包名的形状、包清单的字段、包内引用的边界、装包失败时留下什么，以及壳怎么扫到它。
判据的实现与理由见 [架构](../../../docs/architecture.md) §7.3、§9、§12；
还没做的那一段（SDK 独立发布、装包入口）在 [待办](../../../docs/todo.md) TD-013 与 TD-014。

### Requirement: 包是一个自带清单的归档，文件名由 id 定
依据：id 同时是包文件名前段、userData 下的数据目录名、`airship://<id>/…` 里的那一段，
以及 `relaunchCommand` 里的一个命令行 token——这几处对字符的硬性要求叠在一起，
就是下面这条形状（实测的四类坏法见 `src/shared/app.ts` 的注释）。

#### Scenario: PK-001 id 不合形状，产包期就把规则念出来
- **WHEN** 包清单写 `id: "墨读"`，或写 `"Life"`、`"a b"`、`"a%20b"`
- **THEN** 产包失败，原因原样读得到「id "墨读" 不合形状：只能是 1 到 32 位，小写字母开头，其后只用小写字母、数字与连字符」
- **AND** 同一句里说明界面显示名写在 `name` 字段、那里不限字符
- **AND** 壳侧读清单走的是同一份判定，产出的原因与产包器那句逐字相同

#### Scenario: PK-002 包清单读不出来就是不读，不当成"没有应用"
- **WHEN** 产物目录里没有 `manifest.json`，或那份文件不是合法 JSON
- **THEN** 产包失败，原因点出文件名与缺它还是解析不了（解析不了时带上解析器的话）
- **AND** 包根里不留任何半成品归档

#### Scenario: PK-003 包格式只对得上壳认的那一档
- **WHEN** 包清单 `schemaVersion` 写成 `2`
- **THEN** 产包失败，原因念出「包清单 schemaVersion 只认 1，收到 2」并说明先对齐壳的版本
- **AND** `sdkVersion` 缺失或非空字符串时同样在产包期失败，点名 sdkVersion

### Requirement: 包清单只写应用自己的事实
依据：与 AP-007 同一理由——图标是文件、顺序是应用之间的关系，两者都不是单个应用能决定的。

#### Scenario: PK-004 包清单里没有图标字段，也没有顺序字段
- **WHEN** 包清单出现 `iconPath`、`icon` 或 `order`
- **THEN** 产包失败，原因说清图标是包根那一张文件、顺序由壳按名字典序定
- **AND** 归档根上的图标缺失或多于一张时，原因点出那些条目名

#### Scenario: PK-005 清单里不许有壳不认的键
- **WHEN** 包清单写了一个允许字段之外的键，例如 `capabilitis`
- **THEN** 产包失败，原因点出「包清单有壳不认的键 "capabilitis"」
- **AND** `name`、`description` 缺或为空、`capabilities` 不是字符串数组、
  `defaultWidth` 不是正整数，各自在产包期点名是哪个字段与收到了什么

### Requirement: 包里的东西只能在包内互相引用
依据：包要能在别人机器上离线跑起来，装到机器上的东西不能依赖网络，也不能依赖壳目录树的形状。

#### Scenario: PK-006 入口里指到包外的引用，产包期一条都不放过
- **WHEN** 入口 html 的 `src` 或 `href` 是 `http(s)://…`、`//cdn…`、以 `/` 开头的绝对路径，或解析后越出包根的 `../…`
- **THEN** 产包失败，原因把那条引用原样念出来，并说明包必须自带全部东西
- **AND** `data:` 与 `blob:` 这类内联引用放行，锚点 `#…` 放行

#### Scenario: PK-007 装包失败时旧包原样还在，磁盘上没有半成品
- **WHEN** 装一个新包的过程中失败（清单不合格，或缺入口文件），而机器上已有一个同 id 的旧包
- **THEN** 包根里读得到的还是那个旧包，字节一个没变
- **AND** 文件名列表里不出现 `.tmp-` 或 `.prev-` 结尾的残留

### Requirement: 壳在运行期扫包认应用
依据：改一个应用不该重出整个安装包。名单只有一份，住在主进程；两个包根（开发根与自装根）
的顺序就是优先级，读归档只解需要的那一个条目（不整包展开）。安装包是纯壳，不带应用。

#### Scenario: PK-008 同 id 时先扫到的那份占住，被遮住的写清是谁压了谁
- **WHEN** 开发根与自装根里各有一个 `life.airship`
- **THEN** 生效的是先扫到的那个根里的包，注册表里 `life` 只有一条
- **AND** 原因里读得出被遮住的那一份的完整路径与它来自哪个根

#### Scenario: PK-009 坏包不占名：不合格的那一份压不住能用的那一份
- **WHEN** 优先级更高的根里有一个 `manifest.json` 读不出来的包，另一个根里有同 id 的合格包
- **THEN** 注册表收下合格那一份，应用照常进格子
- **AND** 不合格那一份的原因单独列在问题清单里，不会被静默忽略

#### Scenario: PK-010 暂存与备份归档不算包
- **WHEN** 包根里同时有 `life.airship`、`life.airship.tmp-123`、`life.airship.prev-456`
- **THEN** 注册表里 `life` 只有一条，两个暂存名一个都不算
- **AND** 一级文件名不以 `.airship` 结尾的一律跳过（`specs` 目录、散放的文件同样不算）

#### Scenario: PK-011 没装进来的原因落得下来
- **WHEN** 扫完两个包根，有包没通过校验
- **THEN** 每条原因都是「哪个归档：为什么」的形状，落进日志（`这个包没装进来`）
- **AND** 一个应用都没扫到时日志里读得到「一个应用都没装进来」与找过的那几个包根

#### Scenario: PK-012 发布版忽略 `AIRSHIP_APPS_ROOT`
- **WHEN** 装好的壳（`isPackaged`）带着 `AIRSHIP_APPS_ROOT` 启动
- **THEN** 那个变量不生效，发布版只扫自装根这一个地方
- **AND** 没装的壳（开发运行）下同一个变量生效——不然 `just dev` 就没有包可扫

#### Scenario: PK-013 改了归档名，重启后格子里就没有它
- **WHEN** 把一个已装好的归档改名，再扫一次同一个包根
- **THEN** 注册表里查不到原来那个 id，格子里也没有它
- **AND** 壳与安装包一个字都没动过（这条就是"运行期发现"与"构建期打包"的分界）

### Requirement: 包的文档面只到自己那一个包
依据：`airship://<id>/<相对路径>` 是包对外唯一可读的文件面。
可达范围必须钉在那一个归档里：条目名越界一律拒，也不给"抹掉前缀再试一次"的回落。

#### Scenario: PK-014 越界与没装进来的读取各有各的原话
- **WHEN** 有人请求 `airship://life/../../windows/win.ini`，或请求一个没装进来的 id
- **THEN** 前者解不出任何包外条目（`..`、`%2e%2e`、反斜杠三种写法都验过），后者念「没有注册这个应用：<id>」
- **AND** 两种都拿不到包外的内容，也不回落到入口文档

### Requirement: 把包拖进壳里装
依据：装包的入口只有一个——启动器那一扇。应用窗口不接受拖放，否则任何一个页面拖一下
就获得"往这台机器装可执行代码"的权力，而能力表是给应用的，不是给壳装包的。
落点只有自装根：安装包是纯壳，安装目录里没有应用。

#### Scenario: PK-015 拖进去一个合格的归档，格子里立刻有它，但不自动开窗口
- **WHEN** 把一个 `<id>.airship` 拖到启动器上松手
- **THEN** 自装根里出现这个归档，格子里立刻读得到它的名字，不用重启
- **AND** 没有任何应用窗口被打开——装与跑是两件事

#### Scenario: PK-016 不合格的归档装不上，自装根里也不留它的字节
- **WHEN** 拖进来的归档清单不合格（id 与文件名不一致、`schemaVersion` 不认、缺图标或缺入口）
- **THEN** 启动器上读得到「这个包装不上：<文件名>」与逐条原因
- **AND** 自装根里没有留下这个归档，也没有留下 `.tmp-` 之类的残留

#### Scenario: PK-017 同 id 已在自装根里，不确认就不动原有的那一份
- **WHEN** 拖进来的包与自装根里已装的同 id，而人没有点确认
- **THEN** 界面上读得到「这台机器上已经装了 <名字>（<旧版本>），要换成 <新版本> 吗？」，
  并念得出新包的能力与比旧包多了哪几项
- **AND** 取消之后旧归档的字节一个没变，格子里还是旧的那一份

#### Scenario: PK-018 文件夹与别的扩展名不装
- **WHEN** 拖进来的是一个文件夹，或一个改了名但不是 `.airship` 结尾的文件
- **THEN** 启动器上读得到「这不是 airship 包：<名字>（只认单个 <id>.airship 归档文件，文件夹与别的扩展名都不装）」
- **AND** 不做"帮你猜一下、现场打包"的回落

#### Scenario: PK-019 装完那一行念得出它要了什么
- **WHEN** 一个包装上了
- **THEN** 结果那一行读得到「已装：<名字> · 能力：…」，能力用界面说法（读你的文件 / 跑外部程序…）
- **AND** 清单里 `capabilities: []` 时念的是「能力：不碰你的文件」，不是一句空话
