开发你的第一个应用

准备环境

  • 安装 airship runtime：airship-runtime-Setup-<版本>-x64.exe，下载地址：（留空，待定）。
  • 安装 Node.js：>= 24。

我们的目标

开发一个简单的 todo 应用。它包含一个页面，可以在里面管理你自己的 todo。

第一步 · 创建一个空应用

应用 id 就是项目 package.json 的 name——手脚架把它落成目录名（小写字母开头，小写字母、数字与连字符，最长 32 位）。 后面每条命令都不带 id，认的就是它。 

$ npx create-airship-app my-todo
已建 minimal 项目：C:\Users\…\Temp\my-todo

下一步（都在 my-todo 里跑）：
  npm install            装上 @airship/sdk、@airship/cli 与 react/vite
  npx airship dev        开发模式起窗——改 src 下的源码，窗口里刷新即见
  npx airship start      直跑构建好的产物，与装好后双击快捷方式同一条路
  npx airship pack       产 dist-apps/my-todo.airship
  npx airship installer  产每用户安装器（这台机器要先有 NSIS：winget install nsis.nsis）

前提：这台机器装过 airship runtime（C:\Program Files\airship\runtime），
或把 AIRSHIP_PATH 指到它所在的目录。

落下来的项目一共十个文件：

my-todo/
  package.json          name 就是应用 id，version 就是安装器的版本号
  README.md
  .gitignore
  src/
    app.ts              纯数据清单：id / name / description / capabilities
    App.tsx             组件本体，宿主把 api 当 prop 递进来
    app.css             版心：配色只用宿主给的 CSS 变量
    index.html          入口文档，引 ./main.tsx；里面不写 CSP
    main.tsx            一行 createAirshipApp({ meta, component, icon })
    icon.svg            包根源图：有且只有一张，不套底板
    icon.ico            外壳图标：自己备一张多尺寸的（见第四步）

装上依赖，产第一个包

$ cd my-todo
$ npm install
added 22 packages in 2s

$ npx airship pack
已产包 C:\Users\…\my-todo\dist-apps\my-todo.airship

my-todo.airship 就是 zip 归档换了扩展名；manifest.json 不是手写的，是 app.ts 那份纯数据的投影——改清单永远改 app.ts。

读一读这个起点

清单只写这个应用自己的事实——被驳回过的字段（iconPath、order）不在里面：

// src/app.ts（手脚架起点）
import type { AppMeta } from '@airship/contract'

export const app: AppMeta = {
  id: 'my-todo',
  name: 'my-todo',
  description: '一句话说清这个应用是干什么的',
  capabilities: []        // 唯一授权面，用不到就写空数组
}

入口脚本把清单与组件交给 SDK 宿主，这是应用侧唯一知道"外面有个 runtime"的地方：

// src/main.tsx
import { createAirshipApp } from '@airship/sdk'
import { app } from './app.ts'
import App from './App.tsx'

createAirshipApp({ meta: app, component: App, icon: './icon.svg' })

组件就是普通 React。两条纪律：配色只用 var(--fg)、var(--bg-elev) 这一族宿主 CSS 变量，别写死颜色（否则与标题栏那颗主题键打架）； 想碰系统就经 api. 的对应域，并回 app.ts 把那个能力声明上——没声明的一律拒绝，且拒绝时界面收到的是一句中文人话。

第二步 · 编写应用代码

应用现在只有一颗计数器。把它升级成待办清单，动的就三处：app.ts 加上 backend 能力与入口路径、App.tsx 换成待办界面、新增一份 backend/index.js。airship 的"后端"不是 HTTP 服务：runtime 把清单指的入口起成它自己的一份进程（Electron utilityProcess）， 前后端走消息做请求-回话；它崩了不拖累窗口，窗口关掉它也退出。（npx create-airship-app <目录> --template todo 就是这三处的成品版，拿来对照最方便。）

改完直跑，后端的整条生命周期都在日志里：

$ npx airship start
…
2026-11-23T01:46:32.606Z INFO  [my-todo] 后端程序已落盘 {"entry":"backend/index.js","files":1}
2026-11-23T01:46:32.607Z INFO  [my-todo] 启动后端程序 {"entry":"backend/index.js"}
2026-11-23T01:46:32.610Z INFO  [my-todo] 应用窗口已打开

界面上加一条待办，它就落进 %APPDATA%\airship\apps\my-todo\data\todos.json——每个应用独享 data 目录（后端进程里就是 AIRSHIP_DATA_DIR），别的应用碰不到，卸载也不跟着删。

后端能力是 runtime 后加的。旧 runtime 见到带 backend 的包会整包拒收，报的正是对照表第一条那句 包清单有 runtime 不认的键 "backend"——装最新的 runtime 即可，不是包坏了。

清单里的后端

改后的清单——两个字段是一对：声明了 backend 能力就必须写入口路径，runtime 只在两者齐了以后才起那个进程。

// src/app.ts
import type { AppMeta } from '@airship/contract'

export const app: AppMeta = {
  id: 'my-todo',
  name: '待办清单',
  description: '数据由随包自带的后端写进磁盘 JSON 的待办清单',
  capabilities: ['backend'],
  backend: 'backend/index.js'   // 它在包里的路径，包里必须有这个条目（产包期就查）
}

后端程序

普通 Node 模块，没有框架。全部规矩都在这份范本正文里（注释是模板自带的）：

// src/backend/index.js
/**
 * 线与规矩：
 *   - 启动后**第一件事**发 `{ ready: true }`，runtime 才把调用喂进来；
 *   - runtime 发来 `{ seq, method, payload }`，回 `{ seq, ok: true, value }` 或 `{ seq, ok: false, error }`；
 *   - 数据目录从 `AIRSHIP_DATA_DIR` 拿——只有这个应用那一族碰得到，卸载也不跟着删。
 */
import { existsSync, mkdirSync, readFileSync, writeFileSync } from 'node:fs'
import { join } from 'node:path'

const parent = process.parentPort
const FILE = join(process.env.AIRSHIP_DATA_DIR ?? '.', 'todos.json')

function load() {
  if (!existsSync(FILE)) return []
  return JSON.parse(readFileSync(FILE, 'utf8'))
}

function save(items) {
  mkdirSync(join(FILE, '..'), { recursive: true })
  writeFileSync(FILE, `${JSON.stringify(items, null, 2)}\n`, 'utf8')
}

const handlers = {
  list: () => load(),
  add: (payload) => {
    const text = String(payload?.text ?? '').trim()
    if (text === '') throw new Error('不能加一条空待办')
    const items = load()
    const item = { id: items.reduce((max, t) => Math.max(max, t.id), 0) + 1, text, done: false }
    items.push(item)
    save(items)
    return item
  },
  toggle: (payload) => { … },   // 找不到那条就 throw new Error('没有这条待办')
  remove: (payload) => { … }
}

parent.on('message', (event) => {
  const { seq, method, payload } = event.data ?? {}
  try {
    const handler = handlers[method]
    if (!handler) throw new Error(`后端不认的方法：${method}`)
    parent.postMessage({ seq, ok: true, value: handler(payload) })
  } catch (e) {
    // 回给前端的 error 就是要念给用户听的人话——别回堆栈
    parent.postMessage({ seq, ok: false, error: e instanceof Error ? e.message : String(e) })
  }
})

parent.postMessage({ ready: true })

消息一览：

方向那一行消息什么时候
runtime → 后端{ seq, method, payload }前端每次 invoke 一条
后端 → runtime{ ready: true }启动后第一件事，10 秒内必须发
后端 → runtime{ seq, ok: true, value } / { seq, ok: false, error }对上一条的回话
后端 → runtime{ event: true, method, payload }后端主动推给界面（不需要人问）

环境变量：AIRSHIP_APP_ID、AIRSHIP_DATA_DIR、AIRSHIP_CACHE_DIR。后端要 npm 依赖就写在应用的 package.json 里，随包带着走。

前端怎么调

前端只渲染状态、只发调用，不碰磁盘。一次 invoke 就是一次请求-回话：await 到的就是 handler 的返回值，后端回的 ok: false 原样 reject 成那句人话： 

// src/App.tsx（骨架）
type Item = { id: number; text: string; done: boolean }

/** 把 invoke 的失败收成那句人话：后端回的 error 原样就是给用户的 */
function reasonOf(e: unknown): string {
  return e instanceof Error ? e.message : String(e)
}

export default function App({ api }: { api: AppApi }): JSX.Element {
  const [items, setItems] = useState<Item[]>([])
  …
  async function refresh() {
    try {
      setItems(await api.backend.invoke<Item[]>('list'))
    } catch (e) {
      setError(reasonOf(e))
    }
  }
  async function add() {
    try {
      await api.backend.invoke('add', { text: text.trim() })
      …
    } catch (e) { setError(reasonOf(e)) }
  }
  // toggle(id) / remove(id) 同形；界面上什么都不碰 fs
}

往空输入框点「加上」，handler 里那句 throw new Error('不能加一条空待办') 一路原样回到界面。措辞由后端定，前端只是搬运。

第三步 · 以开发模式运行程序

$ npx airship dev
[airship] 构建 my-todo 的包（注册期只读清单与图标）
[airship] dev server http://127.0.0.1:5177 —— 改 C:\Users\…\my-todo\src 下的源码，窗口里刷新即见
[airship] runtime C:\Program Files\airship\runtime\airship.exe（窗口数据在 .airship-dev/my-todo，不碰日常那套 userData）

这条路上同时有 dev server、被拉起的 runtime、一扇加载 dev server 源码的窗口。终端别急着关——它退出时窗口与 dev server 一起收，留着就是为了看报错。 窗口数据在项目里的 .airship-dev/my-todo，不抢日常那套 userData 的单实例锁。

哪样走包、哪样走源码

  • 前端源码走 dev server：改 App.tsx、app.css 刷新即见，不用重新产包。
  • 清单、图标与后端走包：窗口标题、尺寸、能力、后端入口路径都是 app.ts 的投影，后端进程装的也是包里那份 backend/index.js。 所以改了 app.ts 或 backend/ 要重跑 dev（它开局重新产一次包），只刷新界面没用。
  • dev 的端口默认 5177 且不许静默换端口：同时开两个应用的 dev，给第二个 --port 5178。

直跑带后端的包

想看"和装好后一模一样"的那条路用 npx airship start：文档从包里加载（airship://<id>/index.html），不起 dev server。 第二步里 my-todo 的那三条日志就是这条路跑出来的——后端进程随窗口退出而退出。

第四步 · 发布！

产安装器要这台机器有 NSIS（产包和 dev 都不需要）。没装的话第一条命令会把话说到脸上：

$ npx airship installer
找不到 makensis：装一份 NSIS（例如 winget install nsis.nsis —— 或让 AI 装：「帮我安装 NSIS 并让 makensis 进 PATH」），
或用 --makensis <路径> / 环境变量 AIRSHIP_MAKENSIS 指到它。

三条路：winget install nsis.nsis（或让 AI 装）、设 AIRSHIP_MAKENSIS、每次给 --makensis。指到机器上已有的那份也行：

$ npx airship installer --makensis "C:\Users\xyzwp\AppData\Local\tauri\NSIS\makensis.exe"
已产安装器 C:\Users\…\my-todo\release\apps\my-todo-Setup-0.1.0.exe
SHA256 106fc1489ed6244d5822af1b7cf857150912df6e1c23f1b53bdb20913adf00b1
安装器就绪：C:\Users\…\release\apps\my-todo-Setup-0.1.0.exe（分发给别人前注意：第一次运行会被 SmartScreen 拦一道——没有代码签名）

icon.ico 由你自备

任务栏与快捷方式那颗外壳图标只认磁盘上的 .ico——runtime 不会现场转格式。模板各带一张占位 icon.ico，发版前换成你自己的多尺寸 .ico（16 / 32 / 48 / 256 齐）。源图 icon.svg 仍是"有且只有一张"，.ico 是产物、不算第二张图标。缺了它，产包响亮失败： 

包根没有 icon.ico：任务栏与快捷方式那颗外壳图标只认磁盘上的 .ico

安装器都干了什么

  • 每用户，不要管理员：装进 %LOCALAPPDATA%\airship\apps\my-todo\，桌面与开始菜单各一枚快捷方式（目标是 runtime 的 airship.exe + 包路径）。 它先找 runtime，找不到就中止念出来——装应用不重新送 runtime。
  • 授权在安装期一次完成：安装页念契约层那份能力清单。my-todo 念「跑它自带的后台程序」，装完双击直接开窗口，运行期不再弹确认卡片。
  • 版本号读项目根 package.json 的 version（要盖一次给 --version）；.exe 旁落同名 .sha256；旧包先删再产——宁可报错没有，不许旧包冒充新包。
  • 没有代码签名，SmartScreen 会拦第一次。

分发出去之后

收到 my-todo-Setup-0.1.0.exe 的人只需装过 runtime。他的数据在 %APPDATA%\airship\apps\my-todo\data\todos.json，卸载应用不删它，重装回来待办还在。

报错对照表

本轮实走撞出的，原文照录：

念出来的话为什么怎么办
包清单有 runtime 不认的键 "backend"（要么拼错，要么包格式与 runtime 不同档） 装好的 runtime 是后端能力之前的版本，注册期整包拒收。 装最新的 runtime 安装包。这不是包坏了，重装 runtime 就行。
这个包跑不起来：<文件名>，下面逐条「哪个归档：为什么」 注册判据不合格的统一报法（缺清单、坏 JSON、引用越出包…都从这句出）。 逐条原因就写在下面，照着改清单或产物；改完重跑 pack。
找不到 makensis：装一份 NSIS（例如 winget install nsis.nsis …） 这台机器没有 NSIS（产包不需要，只有安装器需要）。 三条路见第四步：winget 装、AIRSHIP_MAKENSIS、--makensis。
包根没有 icon.ico：任务栏与快捷方式那颗外壳图标只认磁盘上的 .ico 产包期查（外部作者的包不会替你现转格式）。 应用目录放一张多尺寸 icon.ico 再产包；.ico 是产物，不算第二张图标。
包里没有后端入口文件 backend/index.js（清单 backend 指的就是它在包里的路径） app.ts 写了 backend，产物目录里却没有那个条目——后端不在前端模块图里，vite 不会自己搬。 确认文件真在 src/backend/index.js；自己接产包流水的，要把它拷进产物目录。
airship pack 不接 id：id 念的是项目 package.json 的 name，把 "my-todo" 去掉就行 四个动词都不接 id——id 的唯一真源是项目根 package.json 的 name。 命令行去掉 id，直接 npx airship pack。
没有 C:\…\package.json：airship 命令要在应用项目的根目录跑 命令在项目根之外跑，找不到那份 package.json。 cd 进项目根再跑。
app.ts 的 id "other-todo" 与 package.json 的 name "my-todo" 不一致：id 只有一个真源，改齐再产包 产包期两处对照——id 写进了两份文件，只许一处说了算。 把 app.ts 的 id 改成与根 package.json 的 name 相等。
没有 C:\…\dist-apps\my-todo.airship：先跑 airship pack 安装器吃的是已产好的包，包还没产。 先 npx airship pack，再 npx airship installer。
目录名 "My_Todo" 当不了应用 id：只能是 1 到 32 位，小写字母开头，其后只用小写字母、数字与连字符。 目录名就是 id，产包、注册、数据目录同用这一个名字。 换个目录名重来。
C:\…\my-todo 已经存在且不是空目录，手脚架不往里盖东西 防止盖掉你已有的改动。 换目录名，或先把那个目录清空。
