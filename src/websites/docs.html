第一部分

本项目架构

这一部分讲为什么这样搭，以及搭的时候撞过哪些坑。用户可见的契约（界面上读得到哪句话、落盘文件是什么形状）在仓库的规格册里；还没做 / 做不了 / 这期不做的事集中在 docs/todo.md。这一页只讲结构与依据。

系统组成

Airship 是一个 Electron app runtime + 外挂应用 的结构，像 JVM / .NET 那样：运行时只装一份、大家共用，应用是各自独立安装、各自带一个启动快捷方式的小包。八个预置应用的清单与能力声明在预置应用那一页。

runtime 装一次，钉死在 C:\Program Files\airship\runtime（perMachine，要管理员）。应用由它自己的安装器装进每用户目录 %LOCALAPPDATA%\airship\apps\<id>\（不要管理员），安装器在桌面与开始菜单留一枚快捷方式，目标就是 runtime 的 airship.exe 加上那份包的绝对路径。双击快捷方式 → runtime 注册那份包 → 开出这个应用的窗口。

runtime 不认识任何具体应用。跑哪些包由命令行决定（airship.exe <id>.airship，可以一次指多份），注册一份、开一个窗口；没带包路径就念一句用法退出，不存在"开一个空启动器等人挑"这条路。安装包的产物里没有一行应用代码，runtime 自己也没有渲染目标。加 / 更新 / 卸一个应用都不动 runtime。

五个区与依赖方向

区包名管什么
src/runtime@airship/runtime主进程、preload、窗口、能力实现、包协议、单实例转发
src/sdk@airship/sdk宿主（标题栏 / 主题落地 / 留白 / 占位）、图标键、CSP、工装钩子；将来独立发布的那一份
src/apps/<id>@airship/<id>八个应用，各自自持 index.html + main.tsx
src/shared/contract@airship/contract契约、清单类型、拒绝措辞、注册与包形状的规矩
src/shared/library@airship/library共享书库（墨读与 PDF 同一份数据）
src/shared/textdecode@airship/textdecode中文解码
  • 应用与 SDK 不许 import src/runtime/**（用例 AP-013 守着）。runtime 也不 import 任何具体应用——名单来自命令行指来的包。这条由 node 的解析器守：说明符一律写包名（@airship/...），手写别名已全部拆掉。
  • 契约层里 protocol.ts 是 runtime 与应用之间的能力契约（AirshipBridge），这是 airship 唯一重要的文件：应用能做什么全部由这里声明，preload 只按这张表暴露，主进程只按这张表实现。
  • 共享包属于依赖图的下层，反过来依赖 runtime 的界面代码就破了自己定的规则——所以 AppApi（契约 + 自己的 id）放在契约层而不是 runtime 的 UI 层。
  • SDK 是将来要独立发布的那一份，改它的导出等于改公开面。runtime 给应用窗口的 DOM 只有 SDK 那一份——src/runtime 里没有 AppHost，也没有 app.html，更没有启动器。

每个区都是一个 npm workspace 包。根 package.json 只声明 workspaces，没有 scripts；命令只走 justfile。各包的 SDK 与 react 记在 devDependencies——它们被构建进包，运行时不需要机器上装着（AP-016 钉这条）。

七条不变量

这几条是"不照做就会做错"的硬约束，多数有册子编号或用例守着。

  • I-1

    一个应用一个窗口一个渲染进程。隔离是窗口化真正买到的东西：一个应用崩了不带崩别人，改一个应用不用管其余七个。

  • I-2

    应用只能通过 window.airship 碰系统。看不到 ipcRenderer，也拿不到绝对路径以外的系统面；能碰什么由清单 capabilities 声明，没声明的一律拒绝并给出读得懂的原因（措辞在 @airship/contract）。

  • I-3

    身份由 runtime 绑定注入，应用冒充不了别人。preload 从启动参数注入 id，主进程再用 event.sender 反查归属二次确认。应用代码从不传自己的 id。

  • I-4

    数据由 runtime 统一托管。各应用的数据落在 %APPDATA%\airship\apps\<id>\ 下它自己那一族，应用不自己挑落盘位置。共享数据区（书库）由 runtime 创建与托管。

  • I-5

    加一个应用不改 runtime 侧任何文件。名单来自命令行指来的包，不是写死的 id 表。契约层刻意不维护 id 名单（AppId = string，运行期校验）。AP-010 守着：runtime 产品代码里不许出现具体应用 id 的字面量。

  • I-6

    应用与 SDK 不许 import runtime。边界由 node 的解析器守（说明符一律写包名），不靠注释。AP-013 守着这条。

  • I-7

    子进程只跑 runtime 发现的东西。proc 白名单的来历只有一个：runtime 按工具登记表发现的（含环境变量显式指的那一档）。应用既不能自己找一个来跑，也不能借 runtime 发现的名义跑没声明的工具。

能力与边界图

上面七条不变量画在一张图上：从上到下就是依赖方向，珊瑚色那四条是边界——每一道都写着"不照做就会做错"的那件事，以及守着它的用例编号。 能力位（capabilities）是第三道闸门上的东西：应用能碰系统的哪几面，全在那儿声明过才放行。

图上只画边界与判据编号；每条边界的完整理由在下面的小节里——进程与窗口模型讲身份注入与事件路由，契约桥讲那句中文从哪儿来， 能力与授权讲五组能力位各自的判据，包格式讲"引用不许越出包"为什么是硬要求。

进程与窗口模型

单 runtime 进程。所有应用窗口住在同一个 Electron 主进程里，各自一个渲染进程。没有启动器窗口，runtime 自己不画任何界面。

启动流程

  1. 钉死数据目录名

    app.setName('airship')：Electron 的 userData 默认取 package.json 的 name，而那个 name 是 @airship/runtime——不钉住的话书架与设置会在某次升级后"凭空消失"，其实是换了目录。

  2. 抢单实例锁，在 whenReady 之前

    抢不到不是错误——argv 会由 Electron 自动交给第一实例的 second-instance，这次直接 app.quit()。whenReady 首行 if (!GOT_LOCK) return：不然第二实例也会把启动跑完、开出一扇重复的窗再退出（真机抓到过：两扇 dagogo 各开一次）。

  3. 挂协议、注册 IPC、接事件路由

    包协议处理器、IPC 方法、把子进程事件接到"只投归属窗口"的路由上。

  4. 从 argv 挑包路径

    挑出以 .airship 结尾的路径（相对路径按 cwd 解）。一份都没有 → 念用法 + app.exit(1)，不开任何界面。

  5. 逐份注册

    读归档里的清单、校验形状与引用边界、装进活动包表。不合格响亮退出（弹错误框 + exit 1），不静默少一个窗口。

  6. 逐份开窗口

    授权已在安装期完成，直跑不再弹确认卡片。一个窗口都没开出来（全都开失败）→ app.quit()，没有理由继续占着进程。

活动包表是进程级的，只装 argv 指来的那几份包，不扫磁盘。"这台机器上装了哪些应用"不是 runtime 要知道的事——它只知道"这次被要求跑哪些包"。

单实例转发

第二次启动的 argv 转发给已在跑的那一份。相对路径按第二实例的 cwd 解，快捷方式给的是绝对路径不受影响。同 id 同归档 → 复用表里那一份、聚焦窗口；同 id 异归档 → 拒（措辞在契约层）；新包 → 直接开窗口。

窗口、事件与收尾

  • 窗口：无边框（frame: false，标题栏由 SDK 画），尺寸只认清单（没写就跟 runtime 默认 1100×740），位置不记、每次由系统摆。台账判"开新的还是聚焦旧的"。清单 platforms 不含本机的应用根本不开窗口，响亮念出原因。
  • 事件只投归属窗口：子进程进度、托盘点击这类事件只回到归属那个窗口，没有全局广播；窗口没了事件就丢弃。这条抽成纯函数是为了能被测试——隔离的最后一环就是它。
  • 崩溃隔离：一个渲染进程崩了不带崩主进程与别的窗口。主进程的未捕获异常 / 未处理拒绝写日志不致命。
  • 关窗收尾：window-all-closed → 收掉所有子进程、清托盘、退出。截图模式例外——它逐个开窗、关窗再下一个，window-all-closed 在该模式下直接 return，否则截完第一个就退出。
  • 任务栏身份今天是假绿（TD-001）：window.setAppUserModelId?.(...) 是空操作（那方法只挂在 app 上，BrowserWindow 没有），八个应用的任务栏按钮仍共用一个 runtime 身份。
一条踩过代价的运行时不变量：名单来源从构建期改成运行期之后，任何"首次调用时把应用目录 / 能力表快照下来"的缓存都必须跟着作废，否则症状是每个应用报读不到数据（册子 ST-008 钉的就是这个）。

契约桥与 API 面

AirshipBridge 声明应用能碰的全部面：paths / theme / setTheme / settings / dialog / fs / proc / tools / tray / notify / clipboard / log / window / on。 没有 app 参数：身份由该窗口的 preload 从启动参数注入，主进程再用 event.sender 反查归属二次确认。应用既看不到"传 id"这个动作，也就没法冒充别的应用。线格式（preload ↔ 主进程）仍然带 id，那是实现细节，不进契约。

  • AppApi = AirshipBridge & { id }：id 只用于显示与日志，不参与任何权限判定。
  • preload 只暴露 window.airship 这一面。渲染侧拿不到 ipcRenderer，也拿不到绝对路径——路径只能由 preload 的 webUtils.getPathForFile(file) 换出来（拖文件进窗口时用）。
  • 主进程按契约表实现每个方法，按 event.sender 反查归属再查能力表。没声明的能力一律拒绝，错误措辞由 @airship/contract 的 errors.ts 供（中文句子原文，不出现 "Error invoking remote method" 这类 Electron 内部措辞）。
  • 能力位的界面说法（CAPABILITY_LABEL）与人话摘要（capabilitiesPhrase）都在契约层，应用安装器的安装页念它——界面上不许再抄一遍。空清单念"不碰你的文件"，而不是念一个空字符串。
  • 事件频道 ShellEvent：proc:chunk / proc:exit / tray:click / window:maximized。没有 theme:changed 全局广播——主题按应用各记各的，不需要广播。

能力与授权

capabilities 是唯一授权面，没声明的一律拒绝；用不到就写 []（生命游戏就是这么起的）。用了 api.settings. / api.proc. 这些域就必须声明对应能力，AP-011 会扫源码核对。

能力位管什么界面上念作
fs.read读文件：限应用数据目录内，或本次会话中用户通过系统对话框显式选中的路径读你的文件
fs.write写文件：限应用数据目录内写你的文件
dialog弹系统文件 / 目录选择框（选中结果自动进入本应用的可读路径集合）弹系统选择框
settings读写本应用命名空间下的设置项存自己的设置
shared访问 runtime 级共享命名空间（具体哪几个由清单 sharedNamespaces 声明）碰共享数据区
proc派生子进程并接收 stdout / stderr 流跑外部程序
tray托盘图标与提示文字占托盘
notify系统通知发系统通知
clipboard剪贴板读写剪贴板
log写日志（按应用分命名空间）写日志
net应用在自己的窗口里发网络请求（唯一一个不经过桥的能力位，见下）自己连外部服务

net 为什么不经过桥

对象存储的响应里没有跨源许可（要按桶配 CORS，S3 与阿里云 OSS 都这样），runtime 代发就得伪造响应头，而把传输交回渲染侧才能保住流式上传与分块下载。所以请求由应用的文档自己发（fetch），runtime 只做两件事——产包时按清单给它那条放宽了 connect-src 的 CSP，建窗口时按清单给它豁免同源策略。边界仍由清单钉住：没声明的应用拿到的还是收紧那条 CSP，同源策略照旧。

路径授权

五条规则，会话内有效：应用数据目录内随便读写；数据目录外只读用户本次会话通过对话框显式选中的路径；dialog 选中的文件自动进入可读集合（grantParentDir 可连父目录一起授，给"输出落在源文件同目录"那种应用用）；共享命名空间要清单声明；越界直接拒。授权是会话级的，进程退出就没了。

共享命名空间与工具发现

SHARED_NAMESPACES = ['library']，这份名单属于 runtime：目录由 runtime 创建与托管，新增一个共享数据区是 runtime 的功能变更，不是应用变更。墨读与 PDF 是两个独立应用入口，但书架、导入记录、封面、阅读进度是同一套数据——各自存一份就会"同一本书在两个入口里各有一本"。

TOOL_NAMES = ['ffmpeg', 'wslc']，同样属于 runtime。发现顺序三档：环境变量 AIRSHIP_<NAME>_PATH（如 AIRSHIP_FFMPEG_PATH）> PATH > 已知位置。没有"用户指定"那一档（整档随启动器删了），要显式指就走环境变量。工具可用与否在启动第一份日志里就能读到。

子进程接口：proc.run 一次性跑完拿结果（探测类短命令），proc.start 后台跑、进度通过事件回流到本窗口，proc.kill / proc.list 管生命周期；关窗与退出时收掉所有子进程。

包格式与文档加载

归档文件名 <id>.airship——里面是一个 zip，条目名就是包内路径。manifest.json 由产包器从 app.ts 投影，带 schemaVersion（runtime 只认 1）与 sdkVersion。id 的形状、引用不许越出包，产包器（code/pack-app.mjs）与 runtime 侧（@airship/contract）各判一遍，两份由用例比对输出相等来钉。

为什么有两份判据：Node 自己解不开本仓 TS 里那种不带扩展名的相对 import，所以 .mjs 引不了 .ts。也因此，被 Node 直接加载的那几个源码包（@airship/sdk、@airship/contract 等）内部的相对 import 必须写扩展名（./csp.ts）。

包里的东西只能在包内互相引用（PK-006）：入口 html 的 src / href 出现 http(s)://…、//cdn…、以 / 开头的绝对路径、或解析后越出包根的 ../…，产包期直接失败；data:、blob: 与锚点放行。理由：包要能在别人机器上离线跑起来，装到机器上的东西不能依赖网络，也不能依赖 runtime 目录树的形状。

文档面走自定义方案 airship://<id>/<entry>：一个应用只读到它自己那一个包。方案属性在 app ready 之前注册，处理器在 whenReady 里挂。PDF 的 worker 从包里取，EPUB 的章节样式表是 blob:airship://books/…。

CSP 的一个坑：airship:// 下 blob: 的 URL 不再被 'self' 覆盖——style-src 不写 blob: 就被拦掉（截图走查抓到过一次）。CSP 由 SDK 产包时按清单注入，应用的 index.html 里不写 CSP。

归档读取用 fflate：unzipSync(data, { filter }) 只解需要的那个条目，列条目名时 filter 一律返回 false、不解压内容。别改成整包解压——八个包全展开是白给的内存。

数据与存储

全部在 Electron 的 userData（%APPDATA%\airship）下：

userData/
  apps/<appId>/settings.json   应用私有设置（含它自己的主题档）
  apps/<appId>/data/           应用私有数据
  apps/<appId>/cache/          可随时整体删除重建
  library/                     共享书库（墨读与 PDF 同一份）

没有 runtime 级的 settings.json：从前那份全局设置（全局主题、工具手动路径）随启动器退场——主题按应用各记各的，工具"用户指定"那一档整档删了。目录布局只依赖 userData 根与 id，不需要知道"现在有哪些应用"（这条是踩过来的：build() 曾遍历当时的注册表建一张表并缓存，一开机就读失败）。

落盘原子写（写暂存名再改名），坏文件挪成 .bad 不致命。应用安装器卸载不动这份数据；runtime 卸载也不动。

界面与主题

runtime 自己没有界面。应用窗口的 DOM 只有 SDK 那一份宿主：标题栏、主题落地、窗口留白、占位图。应用作者只写自己的正文，标题栏中段念"正在看什么"（书名是应用内容，不是窗口名字）。

主题按应用：三档（亮 / 暗 / 跟随系统）由 SDK 标题栏那颗主题键改，各应用各记各的，落在它自己那份 settings.json，由 theme:set 这条窗口面通道写，不占应用的 settings 能力。"跟随系统"的亮暗判定在 SDK 用 matchMedia 算（主进程没有 matchMedia，不该去猜），setTheme(mode, resolvedHint) 把算好的亮暗传进来。改一个应用的主题不影响别的窗口。

runtime 不记窗口状态（尺寸与位置都不记）：宽高每次按清单的 defaultWidth / defaultHeight，位置每次由系统摆。所以改这两个数立刻生效，也不需要先清掉什么记忆。

构建与出包

两个分发物，互不包含：

  • runtime 安装包 = 清场 → 编译 → NSIS → 自检 + 写 .sha256。perMachine: true（要管理员），落点钉死 C:\Program Files\airship\runtime（目录唯一真源在安装器脚本的 customInit）。因为出包项目根是 src/runtime，安装包文件名只由 src/runtime/package.json 的 version 决定（airship-runtime-Setup-<版本>-x64.exe，主 exe 叫 airship.exe）。runtime 自己没有界面，不留快捷方式，只留控制面板卸载项。
  • 应用安装器 = 先产那一个应用的包，再裹成每用户安装器（RequestExecutionLevel user，不要管理员），落 %LOCALAPPDATA%\airship\apps\<id>\，桌面 + 开始菜单各一枚快捷方式（目标 runtime 的 airship.exe + 引号包路径 + 应用的 icon.ico）。版本读 src/apps/<id>/package.json。

just build-apps 的产物只落在 dist-apps/，不进 runtime 安装包：安装包是纯的，resources/ 里只有 app.asar。出包自检因此钉的是反面——resources/ 里不该有任何 airship 包，runtime 产物里也不该有 out/renderer 或启动器通道。

装包只有一条路：跑应用自己的安装器。安装器先找 runtime（AIRSHIP_PATH > 固定目录，找不到念一句 runtimeNotFound 中止），再念能力清单确认。从前"把归档拖到启动器上"那一族随启动器退场了。

清场是出包入口的第一步：删掉 release/ 里上一次留下的安装包。规矩是宁可响亮报错没有，不许旧包冒充新包。没有代码签名，第一次运行会被 SmartScreen 拦一道。

第二部分

如何为本项目开发软件

这一部分讲怎么在这套规矩下干活：命令走哪里、加一个应用要动哪几份文件、功能怎么先写成契约再写成用例、验证有哪三档、哪些坑已经踩过别再踩一次。开发者的日常对象是一个应用区——按 I-1 与 I-5，改它不需要知道其余七个怎么写的。

环境与起步

要 Windows、Node.js ^20.19.0 || >=22.12.0、just 和 Git Bash。

npm install            # 各区是 npm workspaces，装完自动软链
just                   # 不带参数列出全部配方
just dev life          # 直跑那一个应用：文档热更，清单与图标走包
just check             # 类型 + 单测 + 册子差集

just dev 与截图配方都吃 dist-apps/：改了 app.ts（清单）要重跑一次 just build-apps 才生效，只改组件源码不用——应用的文档在 dev 下走 vite dev server，清单与图标走包。要看"与装好的 runtime 最接近的一条路"用 just start <id>（文档从包里加载）。

动手之前的规矩

  • 命令只走 justfile。package.json 里没有 scripts，别再往回加。
  • 改之前先读对应的规格册（src/<区>/<名>/specs/*.md）。册子是契约，用例是它的影子，不是反过来。
  • 待办只看 docs/todo.md，别处不留零碎待办；编号 TD-### 稳定不复用，做完整条删掉而不是标完成。没人做决定时不要擅自加条目。
  • clean break：不写旧数据迁移、不写兼容垫片。删功能就删干净——整族函数、册子里的契约条目（编号显式删除并写清为什么不再成立）、文档里的行与注释一起收。
  • 工作树里可能有使用者自己正在改的东西：不是这一轮改的文件别动；发现冲突先说清"发布物是否已包含它"，由人挑。
  • 提交由使用者发起，改完停在"未提交"，除非他明说提交。
  • 系统级动作只给命令（覆盖安装、把 runtime 装进 Program Files、重启 explorer 等），由使用者执行。
  • 汇报口径：性能按用户可感知的指标报且要有实测数字；没解决就说没解决，别用"符合设计"辩护；外部引用（法条、格式规范、他人库的行为）先查原文再断言。

一个应用该有的文件

文件规矩
package.json包名 @airship/<id>；SDK、契约、react 记在 devDependencies（构建进包，运行时不需要机器上装着）
app.ts纯数据清单，导出 app: AppMeta；主进程也要读它，所以不带任何组件引用
index.html入口文档，引 ./main.tsx（相对路径）；里面不写 CSP
main.tsx一行 createAirshipApp({ meta, component, icon })
icon.svg|png|jpg|jpeg|webp有且只有一张，不套底板，颜色烘进图里；缺或多在产包期炸
specs/<名>.md + tests/*.test.tsx册子与用例跟着它们管的代码放在这个区里

清单缺哪件产包期炸哪件；图标路径不写进清单（那是文件约定），排序不存在（没有启动器格子要排）。templates/app/ 不参与 just casecov 的双向差集、也不被 vitest 跑，复制进 src/apps/<id>/ 之后才归这套规矩管。

清单怎么写

清单只写"这个应用自己的事实"：

export const app: AppMeta = {
  id: 'hello',                    // ^[a-z][a-z0-9-]{0,31}$：同时是包名前段、数据目录名、airship:// 里那一段
  name: '你好',                    // 界面显示名，不限字符
  description: '一句话说清它是干什么的',
  capabilities: [],               // 唯一授权面，用不到就写空数组
  sharedNamespaces: ['library'],  // 可选：要访问哪个共享数据区（必须同时声明 shared 能力才有意义）
  flush: true,                    // 可选：内容区去掉 runtime 给的默认内边距
  defaultWidth: 1000,             // 可选：不写就用 1100×740，两维各自独立
  defaultHeight: 720,
  platforms: ['windows'],         // 可选：不写 = 全平台
  tools: ['ffmpeg']               // 可选：声明了才拿得到路径，也只有这些进 proc 白名单
}

被明确驳回过的字段别加回来：iconPath（等于假定图标必须是某种形状）、order（顺序是应用之间的关系，单个应用决定不了自己的排位）、窗口状态的记忆（尺寸由 defaultWidth/defaultHeight 定，改了必须立刻生效）。

id 的字符集收严有四条硬理由，实测下来只有这四类会坏：# 与 ? 把 URL 里的 id 截断；% 让校验用的串和要用的目录名分叉；: < > " | * / \ 在 Windows 上做不了目录名；空白进 URL 段整个地址无效。全小写顺带把大小写折叠的撞名消掉。界面显示名在 name，那里不限字符。

代码怎么写

  • 入口只有一行：createAirshipApp({ meta, component, icon }) 把清单与组件交给 SDK 宿主，宿主画标题栏、落主题、按 flush 给不留白。应用侧除了这一行不需要知道 runtime 的存在——这就是"包自持"的意思。
  • 拿 API 用 useAppApi()（src/sdk/api.ts）。它不存在时响亮念出"这个包不是由 airship runtime 打开的，或 preload 没加载成功"，而不是静默空操作。
  • 用不到就别声明能力；用了 api.settings. / api.proc. 这些域就必须声明对应能力，AP-011 会扫源码核对。没声明的调用被拒时，界面上读得到的是契约层那句中文，不是 Electron 内部措辞。
  • 观感用宿主给的 CSS 变量与 useTheme()，别另调一套配色。IconButton / Titlebar / renderTrayIcon() 这些也从 SDK 拿。（Albedo 是"不跟壳主题联动"的显式例外，只此一家。）
  • 需要"正在看什么"就 api.window.setTitle(书名|null)：窗口中段念书名本身，任务栏那侧拼成「应用名 · 书名」。
  • 包内引用不许越出包：入口 html 里的 src/href 必须是相对路径，外部资源要么打进包、要么内联（data: / blob:）。
  • 不要新增手写别名：说明符一律写包名 @airship/...，边界由 node 的解析器守。
  • 改 SDK 的导出等于改公开面（TD-013 挂着独立发布），要动先在架构文档那节说清理由。

规格册

每个功能在动之前先有一份规格册，四档结构：Purpose → Requirement → Scenario → WHEN/THEN。册子是用户可见契约的唯一清单，给人读、给人 review；可执行测试是它的影子，不是反过来。 

#### Scenario: BK-032 MOBI 与 EPUB 走同一条打开动作，书名、作者与章节都落得下来
- **WHEN** 打开一份 MOBI（code/make-mobi.py 造的《道德經》全本样本：扉页 + 两册 + 八十一章）
- **THEN** 读得出书名与作者，切成 84 节，且每一节都有内容（没有空节）
- **AND** 第三节是「第一章」，正文读得到「道，可道也」；第四节读得到「天下皆知美之為美」
  • 只写可观察结果：界面读得到哪句话、错误文案原文、交给外部 CLI 的命令行、落盘文件的形状。✗ THEN settings 缓存命中（键写错也能绿）→ ✓ THEN 重启后读到的还是刚才那本的书号。
  • 不写实现：不出现类名、方法名、控件名——实现变了册子不该变。唯一例外是系统边界上的契约：与 ffmpeg / wslc 的调用契约、与 runtime 的跨进程调用（能力位名、错误文案原文）。
  • 一条 Scenario ≤ 5 行，只锁一个不变量。
  • 编号是稳定句柄：形如 BR-001，按能力前缀分组；不复用、不重排，删除是显式动作，要说清这条契约为什么不再成立。新场景先选节、再取该前缀下的下一个号，所以全局 ID 不保证递增。
  • 界面观感不进册子（宽度、圆角、对齐、真排版好不好看）——那是 just shot 截图走查的事，产物不入代码库。
  • 写不出可执行判据的期望别进册子，记到 docs/architecture.md 对应小节；只能在真机上观察的东西（单实例锁、崩溃隔离、任务栏缩略图）也一样。
  • bug fix 必须先补 Scenario（描述现象），再补可执行用例，再改代码。

现有 23 本：runtime 8 本（bridge / grants / logging / proc-tools / runtime / storage / theme / tray）+ 应用区 2 本（app-model / package）+ 共享 2 本（library / textdecode）+ 应用 11 本（墨读、PDF、打勾勾、生命游戏、vcp、Albedo、S3 各一本，容器台四本）。索引与前缀表见 docs/specs/index.md——新能力的两字母前缀要取没被占用的，索引表里查。

用例与替身

用例标题以同一个编号开头，just casecov 做双向差集：册里有号没用例 = 未实现，用例挂了号册里没有 = 私测（禁止）。差集只看"有没有"，不看次数；同一条契约要多条用例钉住时，编号重复出现即可。 

// src/runtime/specs/runtime.md 里那条叫「SH-006 关掉应用窗口，它名下的子进程跟着收掉」，
// 钉它的用例在 src/runtime/tests/windows.test.ts：
it('SH-006 只杀这个应用的任务，别人的任务一条都不碰', async () => { … })
  • 替身住 SDK，不住 runtime 的测试目录：@airship/sdk/testing 的 FakeAirship 与 mountUi。应用不许引 runtime，用例也不能——否则"包自持"在测试里是假的；而且外部作者复制范本出去后要拿到同一个替身。
  • 替身只能实现真 API 面上存在的方法。两条教训：替身窗口写过 setAppUserModelId（BrowserWindow 上根本没有这个方法），用例绿着而真机没生效；window.x?.() 这种可选链会把"方法不存在"吞成静默空操作——缺什么要喊出来，别默默跳过。
  • 挂载器按"用户看得见的话"断言，故意不引第三方测试库：mountUi(<App api={fake.api} />, { fake }) → m.text() / m.type(...) / m.press('添加')。异步链路靠 settle() 把微任务与定时器跑干净再断言。
  • jsdom 没有 2D canvas：画布类判据只断言文字、状态与几何数字，"真画出来了"归 just shot。
  • 整面 vi.mock('@airship/sdk', ...) 会把 SDK 的其他导出一起抹掉（踩过：useTheme 凭空不见）。要部分替换就用 vi.mock('@airship/sdk', async (importOriginal) => ({ ...(await importOriginal()), ... }))。
  • 真素材跟着用例走，放在该区 tests/fixtures/；仓库根不留 fixtures/。
  • 需要真环境的用例门控：按环境变量跳过（VCP_E2E=1、AIRSHIP_WSLD_INTEGRATION=1），标题里照样带编号——静态扫描算它已实现，跑没跑由那档变量决定。外部服务的替身要被证明真接住了请求：S3 那条链路起一个真跑在 127.0.0.1 上的假 S3 服务，因为换 globalThis.fetch 拦不到 AWS SDK，早期版本因此把请求发到了真端点。

截图模式几条要记住的：

  • 只有截图那一条命令会先构建。裸跑截图命令截的是上一次留在 out/ 的构建——看着像"改动没生效"。
  • 等待要够长：冷启动的外部命令实测可以到 2.5 s，等 1.5 s 永远截成空壳，看着像应用有 bug。报"某功能坏了"之前先排除工装时序与文件系统抖动，连跑两遍全绿再下结论。
  • 截图只拍视口；折叠线下的那一栏要临时改窗口高度，看完还原并重新构建。
  • hover 才出现的东西，截图模式驱动不了鼠标：只能临时加一句"自动展开"，看完还原、重建，并确认 git status 里没有补丁残留。
  • 喂真素材走 AIRSHIP_AUTOTEST='{"app":"...","path":"C:/..."}'（值是 JSON，路径必须写正斜杠；反斜杠解出来是 \U，解析失败后只打一句"忽略"，截图看起来像功能没做）。那份档案是独立的 airship-shot-profile，写进正常 userData 读不到。
  • 验证报告要说清：哪一半靠用例、哪一半靠像素、哪一半没验到。临时补丁必须还原并重建后才算交付。

出包与分发

just build-apps            # 八个包 → dist-apps/<id>.airship
just app-installer books   # 先产 books 那份包，再裹成每用户安装器
just build-runtime         # 清场 → 编译 → NSIS → 自检 + .sha256（纯 runtime）
just build                 # 两条一起跑
  • 先跑过一次 just build-runtime 再产应用安装器：应用安装器用的 makensis 是 electron-builder 缓存里那份。
  • 两个分发物互不包含：安装包是纯 runtime，应用包只落在 dist-apps/ 并由各家自己的安装器装。
  • 授权在安装期一次完成：装前念能力清单（措辞由 @airship/contract 供，别在界面或 NSI 里另写一份），装完双击快捷方式直接开窗口。
  • src/runtime/out/、dist-apps/、release/、shots/ 都不入库，根目录保持干净；中间产物写到系统临时目录。
  • 没有代码签名（TD-003），也没有自动更新链路（TD-004）。

版本号规矩

只有两条：

  • 根 package.json 与 src/runtime/package.json 保持一致——它们是同一个发布物，就该念同一个数（现 0.4.0）。产包器取根那份当包清单里的 sdkVersion，两处不一致等于清单在说谎。
  • 各应用自己的 package.json 版本独立演化，不跟 runtime 跳：一个应用发自己的版不该惊动别的区和 runtime。

runtime 的 package.json 里 electron 必须写固定版本（45.2.3，不带 ^）——electron-builder 要按它下载对应平台的二进制，写范围会直接被拒。

踩过的坑

症状成因与规矩
import * as x from '@airship/sdk/testing' 拿到空对象而不是报错源码包被 Node 直接加载时解不开省略扩展名的相对 import。这些包内部写 ./foo.ts / ./foo.tsx；vitest 那边还要 server.deps.inline: [/^@airship\//]。
包工装"静默失效"、注册表"安静地空着"mkdtempSync 在 node:fs 不在 node:os；从 os 引拿到 undefined。用例的包目录每次新开一个临时目录，不按 pid 复用——Windows 上 rmSync(force) 会把"删不掉"咽下去，旧格式残包留在原地。
useState 读到 nullworkspace 软链进 node_modules 后，rollup 的 commonjs 互操作会把 react 各包一遍。三份构建配置都写了 resolve.dedupe: ['react','react-dom','react/jsx-runtime']，摘掉就崩——别按"看起来多余"删它。

暗色模式下书叶还是白底EPUB 自带 CSS 会盖过渲染器那层，只能往每节文档注入带 !important 的纸面样式，换主题时对已渲染页重打、新页在 load 里补。
封面画成破图靠 file:/// 拼地址会被应用窗口 CSP 拦掉；改成 api.fs.read 拿字节 → blob: URL。airship:// 下 blob: 不被 'self' 覆盖，style-src 要写 blob:。
Python 脚本打印 ✓ 或韩文报 UnicodeEncodeError控制台默认 GBK：脚本里用 ASCII 或中文（GBK 能编码）；乱码输出不代表文件坏了。PowerShell 5.1 读无 BOM 的 UTF-8 .ps1 按 GBK 解，所以 .ps1 要纯 ASCII。Git Bash 的 MSYS 路径转换会破坏 NSIS 的 /S，静默安装走 cmd //c "set VAR=...&& prog.exe /S"。
Pillow 不认 SVG，无头 Chrome 截内联 SVG 出空白要 SVG→位图用 @resvg/resvg-js；应用安装器把包内 SVG 经 resvg 出 256 PNG，再转多尺寸 .ico。
just dev 里看到 undefinedp 这类怪值先怀疑热更新：React Fast Refresh 会保住已挂载组件的 useRef，改了 state 形状后旧进程里还是老形状。截图模式每次是新进程，所以只有直跑那边会看到——重启一次，别写防御性代码。
界面上"设置像没存过"但画得好好的截图模式用的是 %APPDATA%/airship-shot-profile，要喂真数据得灌进那份档案。
托盘徽标只更新了提示文字Windows 托盘图标是位图，主进程没有画字的能力；要画出带数字的图标，应用侧用 renderTrayIcon() 生成 iconDataUrl 一起传。

收尾检查单

  1. 新改动有没有对应的册子场景？bug fix 先补 Scenario，再补用例，再改代码。
  2. just check 全绿（类型 + 单测 + 差集双向零缺漏）。
  3. 动了界面观感？跑 just shot 走查截图，确认临时补丁已还原并重建，git status 干净。
  4. 加了新能力位或新工具？那是 runtime 的变更，不是应用侧改一条字符串就算——工具名单与共享命名空间名单都属于 runtime。
  5. 改了 SDK 导出？等于改公开面，同步 docs/architecture.md 对应小节。
  6. "还没做 / 做不了 / 这期不做"记进 docs/todo.md（只在有人做了决定时）；架构文档里只留状态标记，不另开一章。
  7. 停在"未提交"，把改动、验证口径（哪一半用例、哪一半像素、哪一半没验到）和实测数字讲清楚，由使用者决定提交。
